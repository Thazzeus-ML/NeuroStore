# DECISIONS

Every design choice made without asking, in the order made. Format: **D<n>** decision — reason.

**D1** Work in `./neurostore` (created under the session working directory `/home/user`). Python 3.13, NumPy 2.5, pytest, hypothesis; no other dependencies.
**D2** Gates live in `gates.toml` and are *read* by the experiment scripts (`eval/gates.py`), so a gate verdict cannot silently drift from the committed threshold. Each phase has two commits: a `prereg:` commit containing only the gate, then the phase commit with code, tests, results and the verdict.
**D3** Gate runs use seeds 0-4. Seeds >=100 are dev seeds used to debug and to choose hyper-parameters on a validation stream; they never appear in gate numbers. Hyper-parameter sweeps are done on validation streams (never the held-out test stream) and are logged in `results/`.
**D4** World defaults: F=800 raw features, C=40 concepts, M=20 members, p=0.7, Poisson(3) noise, 1/2/3 concepts with prob .6/.3/.1, chain stay=0.5 + 3 preferred successors (mass 0.3) + popularity background. Chosen so concepts overlap by chance in raw features (F is small relative to C*M=800) and the task is not trivially separable. Not tuned against any system result.
**D5** Noise features are Poisson(noise_mean) uniform draws with replacement. Reason: per-feature presence is then independent Poisson, which gives an exact analytic mean feature count to test against.
**D6** Extra (2nd/3rd) concepts are drawn from the popularity distribution, not the chain; only the primary concept has sequential structure. Anomaly events (optional) are pure-noise events with no concepts and do not advance the chain.
**D7** Streams are addressed as (split, idx): train/val/test/extra use disjoint SeedSequence streams. With drift enabled, a train stream switches membership at n//2; test streams are generated with a fixed phase (0 = pre-drift, 1 = post-drift).
**D8** Phase 0 gate: PASS on seeds 0-4 (results/phase0.json).
**D9** Encoder = fixed seeded random sparse projection (each raw feature -> d=2 of N=1024 units) + per-unit adaptive threshold, k-winner-take-all on margin = score - theta + tiny fixed jitter (jitter makes ties deterministic and pseudo-random rather than low-id-first). Score = number of active features projecting to the unit. k=32 (3.1% of N). The encoder is not learned: all learned structure lives downstream (assemblies, synapses).
**D10** Spike strength = unit score / max score in the event (0 for filler units that won only on threshold/jitter), quantized to uint8; surprise is uint8 too. Log t is float32. Volley bytes per event are 8 + 4k.
**D11** Volley tiles are allocated in slabs of 64 tiles x 64 volleys (4096 events) so growth never copies sealed data. All layouts store fixed width k per event.
**D12** `soa_event` (event_id/t stored once per event, spike arrays hold only unit/strength/surprise) is added as a control layout beside the three requested baselines. Reason: it separates the benefit of volley *tiling* from the benefit of merely not repeating event_id and t on each spike.
**D13** Gate 1's bytes criterion is nearly tautological for a fixed-width format; it is kept because the spec asks for it, and the REPORT says so. The informative Gate 1 number is the same-vs-different-concept overlap.
**D14** Gate 1: PASS (results/phase1.json). Mean code overlap same-concept ~0.54 vs different-concept ~0.06 (chance k/N = 0.031). Unit firing-rate CV without homeostasis ~1.2.
**D15** (dev seeds 100-101 only, before the gate-2 run) First assembly design gave 160 assemblies for 40 concepts (fragmentation) and masked-unit precision 0.38 vs 0.55 for the kNN reference. Diagnosis: a concept's true unit profile has ~40 units firing >=0.3 but each assembly held ~20, because exclusive-claim credit let two fragments of one concept partition its units, and cosine-based merging cannot merge disjoint halves. Changes: (1) merge fragments that co-explain the same events (co-match ratio >= 0.5, min support 8) with elementwise-max weights; (2) removed claim-denial credit (`asm_claim=False`); (3) member threshold 0.3 -> 0.2. Dev result after: ~76 assemblies, median size 34, P@m ~0.51, F1 ~0.90. Total dev sweeps: 3 rounds of <=6 variants each. Caveat recorded for REPORT: removing claim-denial is only safe because the synthetic world draws extra concepts independently; with strongly correlated concepts the contamination risk returns.
**D16** The pre-registration for phase 2 had a TOML typo (`{0.3 = 0.90}` parses as a nested table). Fixed by quoting the keys in a separate commit, values unchanged, before any gate-2 run.
**D17** Phase 2 uses `replay_budget=200` = `consolidate_every` so every training event is replayed once (budget not binding), and no surprise gating, no homeostasis, no synapses.
**D18** Gate 2: **FAILED** (5 of 6 conditions pass). The failing condition is masked-unit precision at mask 0.3: NeuroStore / kNN-reference ratio 0.862 vs 0.90 required. Diagnosis (bench/phase2b_diagnosis.py, dev seeds): completion from assembly marginal profiles cannot use within-event pair structure (the encoder maps each raw feature to 2 units, so a visible unit implies its partner fired). An oracle that boosts those partners lifts NS from 0.43 to 0.49, equal to kNN-10 (0.49). Two in-scope good-faith fixes were tried and gave nothing: sharper assembly weighting (cos^3), member threshold 0.1. The third candidate fix is the synapse lattice itself (within-event co-firing edges); it belongs to phase 3, so it is reported there as a post-hoc follow-up measurement. The Gate-2 verdict is NOT changed by it.
**D19** Lattice implementation: CSR (layouts/csr.py) + COO delta chunks indexed lazily; lazy decay by per-edge epoch and a (1-lambda)^n table; epoch = one consolidation round; merge() folds delta in without changing decayed values (so reads before/after merge agree) and prunes to the top R=128 out-edges per pre unit. Merge uses dense N x N scratch arrays (O(N^2), fine at N=1024, would not scale). Hebbian increments for a replay batch are computed with matrix products (A^T A plus lag-weighted P^T A), then written to the delta buffer. Row-normalised reads (weights divided by the pre unit's out-weight sum) are a read-time choice, selected on validation.
**D20** Gate 3: **PASS**. Mean recall@32 NeuroStore 0.253 vs bigram 0.228 vs global frequency 0.161 (oracle with true chain and profiles 0.326); NeuroStore wins on 5/5 seeds. Read parameters were selected per seed on validation (hops=1 won on every seed).
**D21** Post-hoc controls (bench/phase3c_controls.py, run AFTER the gate result, cannot change it): removing within-event edges drops recall 0.253 -> 0.206 (below the bigram); a single lag instead of the pre-registered three IMPROVES it to 0.268; an unpruned, non-decaying dense matrix gives 0.257. So the advantage over the bigram comes from within-event co-firing (pattern completion), not from decay, pruning or the multi-lag temporal structure. The sparse lattice (R=128, ~10% of edges, 5.5x smaller) loses nothing measurable against the dense one. The pre-registered n_lags=3 was a worse choice than 1; it is left as is.
**D22** Post-hoc completion follow-up (bench/phase3d_completion_followup.py): mixing lattice spread into masked-unit completion lifts the mask-0.3 ratio only from 0.862 to 0.868 (needs 0.90). My D18 expectation that the lattice would fix it was NOT confirmed in the implemented form, although the sibling-oracle diagnostic shows the information is there. Gate 2 stays FAILED.
**D23** Drift (bench/phase3b_drift.py, reported only): at the drift point recall on the post-drift test stream is ~0.17 vs ~0.26 on the pre-drift stream. After 4000 more events NeuroStore with lambda=0.03 reaches 0.227 and never regains 95% of its pre-drift level; lambda=0.15 reaches 0.249 and regains it in 4/5 seeds (1600-4000 events) but its pre-drift-stream recall falls to 0.185 (forgetting the old world). A 1500-event windowed bigram reaches 0.221; the cumulative bigram 0.210.
**D24** Write path (phase 4): normalize -> encode -> homeostasis update -> predict (from the previous event) -> surprise S = (|fired\expected| + |expected\fired|) / (|fired| + |expected|) -> gate (stored iff S > tau; count-only otherwise) -> append with strength = raw strength * max(floor, S) -> rates (always updated, also for count-only events) -> mark hot (S >= hot_tau, or the best assembly was matched >= 3 times since the last round). Count-only events add nothing to the log, so the lagged Hebbian pairs across them are lost (the replay only sees stored neighbours).
**D25** Gate 4 attempt 1 (expectation = lattice spread from the previous event's best assemblies, cached per context key): **FAILED** on bytes: reduction 18.3% < 20% required (recall unaffected: F1 and P@m drops about 0, tau grid topped out at 0.55). Diagnosis (dev seeds, bench scratch): mean surprise 0.74; 0.58 even when the primary concept repeats, 0.90 when it changes; an oracle that knows the current concept's top-32 profile reaches 0.40 (0.30 for single-concept events). Good-faith fix 1 (of max 3): expect persistence of the previous event's best assembly (top-32 members by weight) instead of lattice spread; the lattice is only the cold-start fallback. Attempt 2 (same thresholds, same grid, same seeds): **PASS**, bytes -29.4%, F1 drop -0.009, P@m drop -0.007 (negative = the gated system is slightly better). Both result files are kept (results/phase4_attempt1.json is the failed first attempt; results/phase4.json is attempt 2). Fix 2 and 3 were not needed.
**D26** Findings to carry into the report: (a) the learned synapses are a WORSE predictor of the next event's units than simply assuming the previous assembly persists (51% of consecutive events share the primary concept); (b) the gated system's recall is not worse, and nominally slightly better, plausibly because replay is concentrated on surprising events, but the difference is within seed noise and the mechanism was not tested; (c) the gate saves log bytes only: rate counters still update on every event and the replay still writes lattice deltas (bytes_delta_written is recorded in results/phase4.json); (d) homeostasis cuts the CV of per-unit firing rates under Zipf skew by ~97% (ratio 0.03 vs <=0.7 required) with k exactly fixed. That very strong equalisation may cost code content; checked in phase 6.
**D27** Phase 2/3 scripts pin `hot_tau=0.0` (and the drift script `replay_budget=200`) so that every stored event stays hot, as when those results were produced, after the real surprise was wired into the write path. Verified: the phase-3 gate numbers reproduce bit-for-bit.
